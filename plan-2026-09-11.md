# pi-harness: pin, verify, and share harness resources across projects

**Date:** 2026-09-11
**Status:** Draft -- pending review

This is an extension of `pi-harness`, not a new project: three
additions that keep the harness *steady* -- pinned so it doesn't drift,
verified so its claims are recorded, and shared so the same skill doesn't
get rewritten per repo. Each piece lands as ordinary extensions, skills,
prompts, and tests in this repo, under the existing layout. It is not a new
repo and not a new runtime.

Origin: a comparison of this repo against a team-oriented harness/config
layer another project is planning to integrate. That layer bundles six
things -- context management, resource discovery, configuration bridging
(repo MCP settings into pi's MCP adapter), reproducibility (pinned pi and
package versions), team consistency (shared agents/skills/prompts with
auto-update), and an optional evidence-loop `/verify` pack. This plan
cherry-picks three of them for a solo developer and says why the rest are
not built now.

## Goal

Three additions, each buildable and testable on its own, in this order:

1. **Reproducibility.** A harness that works today keeps working after a
   `pi update` or a `git pull` of a sibling repo, or says loudly why it
   won't. Pins are declared once, checked mechanically, and moved on
   purpose.
2. **Evidence loop (`/verify`).** The self-review discipline already done by
   hand (`/before-done`, `/review`, the "re-run the verification command
   yourself" rule in README's dispatch section) becomes something the
   harness *runs and records* -- deterministically, bound to the diff it
   checked -- without ever gating a turn or overriding the user's judgment.
3. **Cross-project resource discovery.** Skills and prompts that already
   exist in one config repo (this one, `hermes-config`, `agent-configs`)
   become loadable in a pi session for any project through one declared
   registry, instead of a second hand-written copy per repo.

Out of scope, with reasons, in "Decisions and non-goals" below.

## What already exists

Grounded in the current tree, `README.md`, `AGENTS.md`, `install.sh`,
`package.json`, and pi 0.84.2's bundled docs (`node_modules/@earendil-works/
pi-coding-agent/docs/{packages,skills,settings,extensions}.md`).

### Install and versioning

- Two install paths, documented as kept in sync on purpose: `pi install
  git:github.com/ljammula/pi-harness` (README Quick start) and
  `./install.sh` (symlinks into `~/.pi/agent/`). Nothing *enforces* that
  `package.json`'s `pi` manifest and `install.sh`'s link lists agree;
  `tests/install-scope.test.ts` tests only the symlink side.
- The README's `pi install` line carries **no `@ref`**. Per pi's
  `packages.md`, an unpinned git package floats to the default branch on
  every `pi update --extensions` / `--all`; a pinned ref (`@tag` or
  `@commit`) is reconciled but never moved. The repo has **no tags** yet.
- `package.json` pins the four `@earendil-works/pi-*` devDependencies at
  exactly `0.84.2` (typecheck/test target), with `"*"` peerDependencies as
  pi's packaging docs require. The `pi` binary on `PATH` is a separate
  global npm install, also `0.84.2` today -- the two can diverge silently,
  which the private upgrade runbook (`agent-configs/pi-version-upgrade-plan.md`,
  not in this repo) found live during the 0.83.0 -> 0.84.2 bump.
- On this machine `pi list` reports no packages: the live `~/.pi/agent/`
  is symlinked into the private source repo (`agent-configs/pi`), from
  which this public repo was extracted. `diff -rq` shows the two have
  already drifted in 7 extensions and 6 skills, plus two project-specific
  skills that exist only privately. That drift is the concrete version of
  "resources shared by copying diverge."

### Verification and evidence

- `skills/before-done/SKILL.md` + `prompts/before-done.md`: the manual
  completion gate. The prompt already defines the report shape this plan
  formalizes (`ran: <cmd> -> <result>` / `skipped: <cmd> -> <why>` /
  `verdict: DONE | NOT DONE`) and the rule "a check you did not run is
  `skipped`, never `pass`." It relies entirely on the model pasting real
  output; nothing durable records it.
- `prompts/review.md`: read-only diff review with a `CLEAN | NEEDS WORK`
  verdict line. Same property: the verdict lives only in chat.
- `extensions/quality-gate.ts` + `extensions/lib/verification.ts`: the
  deterministic half already exists. `resolveVerificationCommand` finds the
  canonical broad check; `snapshotDiff`/`evidencePassesCurrentDiff` bind a
  passing result to the diff hash it postdates;
  `verificationPipelineCanMaskFailure` rejects `| head`-style masking
  without `pipefail`; truncated output is inconclusive. Its header comment
  documents the decision *not* to nudge or gate from inside the session
  (a `followUp` message cannot interrupt a model that keeps calling tools),
  and to "verify and report truthfully" instead.
- `extensions/lib/harness-telemetry.ts`: `appendHarnessTrace` writes
  versioned `pi-harness-trace` entries into the session file via
  `pi.appendEntry` -- event (`verification`/`review`/...), outcome,
  `diffHash`, duration, no prompts or source. This is the existing record
  format; it is machine-facing, not something a human reads at the end of
  a task.
- `extensions/cross-model-review.ts`: optional blind second opinion,
  bounded to 3 rounds, labeled `independent-review` only when the reviewer
  route is a genuinely different model.
- A **dangling reference**: `before-done` step 6 and `self-review` step 2
  both invoke `scripts/local-review.sh` (under `skills/before-done/scripts/`),
  which does not exist anywhere in this repo. It stayed behind in the
  private source during extraction.

### Resource discovery

- pi natively loads skills from `~/.pi/agent/skills/`, `~/.agents/skills/`,
  project `.pi/skills/` and `.agents/skills/`, package `skills/` dirs, the
  settings `skills`/`prompts`/`extensions` string arrays (globs and
  `!exclusions` supported, directories allowed), and `--skill <path>`.
  `skills.md` explicitly documents pointing the `skills` array at other
  harnesses' directories (`~/.claude/skills`). Name collisions warn and
  keep the first skill found.
- The `resources_discover` hook (fires after `session_start`, again on
  reload) lets an extension contribute `skillPaths`, `promptPaths`, and
  `themePaths` -- not extension paths. This repo already uses it twice:
  `stack-skill-overlay.ts` surfaces only the stack skills a repo's evidence
  matches, and `project-skill-overlay.ts` surfaces the six project skills
  only when the origin remote matches `PI_PROJECT_SKILLS_REMOTE`. Both exist
  because README records that advertising every skill in every session is
  a measurable startup-token tax on a 64K-96K context model.
- Duplication is real today, not hypothetical: `karpathy-guidelines` and
  `wiring-verify` exist as separate, diverged copies in `hermes-config/skills/`
  (Hermes-flavored frontmatter, 97 lines) and here (152 lines);
  `~/.claude/skills/` is a hand-made mix of symlinks into `agent-configs/pi`
  (`before-done`, `wiring-verify`) and `agent-configs/claude` (`docs-verify`,
  `karpathy-guidelines`, `local-summarize`). Cross-repo sharing already
  happens -- by hand, per machine, with no record of which copy is canonical.

### Not present

- No MCP servers configured, and `pi-mcp-adapter` is deliberately not
  installed ("install it when you actually have an MCP server to adapt").
- No multi-developer distribution of any kind; every consumer of this
  config is the same person on the same machines.

## Decisions and non-goals

1. **Cherry-pick three pieces; do not clone the team harness.** Three of
   its six features solve problems visible in this repo today (an unpinned
   install line, verdicts that exist only in chat, diverged skill copies).
   The other three solve problems a solo developer does not have. Building
   them anyway would be exactly the speculative abstraction
   `karpathy-guardrail.ts` enforces against on every session.
2. **Non-goal: team consistency / shared distribution with auto-update.**
   It exists to keep N developers' configs converged. Here N=1, and the
   existing mechanisms (`pi install git:...@ref`, `install.sh`, `git pull`)
   already converge one person's machines. The cost is not zero either:
   auto-update is the opposite of piece 1's pinning, and reconciling the
   two would be work spent on a conflict that only exists because the
   feature was built. Revisit only if a second contributor appears.
3. **Non-goal (watch item): MCP configuration bridging.** It bridges
   per-repo MCP settings into pi's adapter. No repo here declares an MCP
   server for pi, so there is no friction to remove yet. The trigger for
   promoting this to scope is concrete: the second time an MCP config is
   hand-wired for a repo, write it up as a plan. Until then this stays a
   line item, consistent with README's existing "not before" stance on the
   adapter itself.
4. **Non-goal: a context-management merge layer.** pi already layers
   global `AGENTS.md`, project `AGENTS.md`, and (since 0.84.0)
   `AGENTS.override.md`. The team harness's base/team/personal/repo merge
   adds a "team" tier this repo has no writer for. Nothing to build.
5. **`/verify` records; it never gates.** This is a design constraint, not
   a phase-1 simplification. Two reasons already documented in this repo:
   `quality-gate.ts`'s header (in-session correction via `followUp` cannot
   interrupt a tool-calling model, so the extension's scope was narrowed to
   truthful reporting) and `goal-gate.ts`'s (a same-model completion judge
   carries self-report bias). The user's own judgment stays the gate;
   `/verify` makes what that judgment is based on durable and honest.
6. **`/verify` runs the checks itself; it does not ask the model to.**
   `prompts/before-done.md` exists because "a small model told to run the
   gate will report success without running anything." A recorded verdict
   is only worth having if the record was produced by `pi.exec`, not by the
   model narrating. The model's job after `/verify` is to read the record
   and decide, same as a human would.
7. **Version pins warn; they do not refuse to load.** A hard refusal on
   version mismatch would turn a routine `pi update --self` into a
   harness outage with no session to diagnose it from. A one-line
   `ctx.ui.notify` warning at startup plus a `startup` trace entry is
   enough for one person to notice and act.
8. **Discovery is an explicit allowlist per root, never "load everything
   under that directory."** `hermes-config/skills/` holds ~30 skills, most
   Hermes-specific (email, smart-home, gaming). Globbing it in would
   recreate the startup-token tax `stack-skill-overlay.ts` was built to
   remove, and would import skills whose tool names do not exist in pi.
   Same shape as `project-skill-overlay.ts`: a short named list, a no-op
   when unconfigured.
9. **Pick one canonical copy per shared skill, and make the others
   references.** Two independently edited `wiring-verify` files are worse
   than one, whichever one it is. This plan makes *pi* read the canonical
   copy; it does not change how Hermes loads its own skills (different
   runtime, different frontmatter conventions) -- that is a follow-up in
   `hermes-config`, noted below, not part of this plan.
10. **Build inside this repo, not a fourth config repo.** The user is
    already juggling three. Every piece here hooks existing modules
    (`lib/verification.ts`, `lib/harness-telemetry.ts`, the overlay
    pattern) and ships through the existing `install.sh` / `pi` manifest /
    `tests/` paths. A separate repo would immediately need piece 1 and
    piece 3 applied to itself.
11. **Order: pin, then verify, then discover.** Pinning is the cheapest and
    protects the other two from drifting while they are built; `/verify` is
    the highest-value single addition and reuses the most existing code;
    discovery touches the most machines and benefits from `/verify`
    existing to check it with.

## Plan

Each step names its verification. "Test" means an addition under `tests/`
run by `npm test`; "live" means a `pi -p` run against a scratch directory.

### Piece 1 -- Reproducibility

- **1.1 Tag a release and pin the install line.** Cut `v0.1.0` at the
  current `main`. Change README's Quick start to
  `pi install git:github.com/ljammula/pi-harness@v0.1.0` and add
  one sentence on moving to a new ref (`pi install ...@v0.2.0`, which pi
  documents as the way to update a pinned git package). Live: on a scratch
  `HOME`, `pi install` the tag, run `pi update --extensions`, confirm the
  checkout still sits on the tag.
- **1.2 Manifest-sync test.** A test that parses `package.json`'s `pi`
  manifest and `install.sh`'s `PORTABLE_SKILLS`/`DISABLED_EXTENSIONS`
  lists and asserts they describe the same set of skills and the same
  excluded extensions. README already promises they are in sync; this
  makes the promise fail loudly instead of drifting. Test only.
- **1.3 Lockstep pin test.** A test asserting the four `@earendil-works/*`
  devDependencies are the same exact version (no `^`/`~`) and that
  `package-lock.json` resolves each to that version. Cheap guard against
  bumping one of four cross-dependent packages. Test only.
- **1.4 Runtime pin check (`extensions/harness-pin.ts`).** On
  `session_start` with `reason: "startup"`, resolve the running
  `@earendil-works/pi-coding-agent` version (from the peer module pi
  loads the extension against, not by shelling out to `pi --version`)
  and compare it to the pinned devDependency version read from this
  repo's own `package.json`. On mismatch: one `ctx.ui.notify` warning
  naming both versions, and one `startup`/`unconfigured` trace via
  `appendHarnessTrace`. Never throws, never disables anything (decision 7).
  Test: unit test through `tests/extension-api-harness.ts` with the
  version pair injected; live: confirm no warning on a matching install.
- **1.5 Upgrade runbook in-repo (`UPGRADING.md`).** A public version of the
  private runbook's procedure, stripped of private eval-battery references:
  bump all four packages with `--save-exact`, bump the global CLI, `npm run
  typecheck && npm test`, one live `pi -p` smoke run on a scratch repo,
  tag, update the README install line. Include rollback (`git checkout --
  package.json package-lock.json && npm install`). Doc only; 1.2-1.4 are
  what make it checkable.

### Piece 2 -- Evidence loop (`/verify`)

- **2.1 Command, not prompt template (`extensions/verify-pack.ts`).**
  Register `/verify` as a real slash command, for the same reason
  `goal-gate.ts` is one: it needs to run commands, hold the result across
  the turn, and write records -- none of which a `.md` template can do.
  Subcommands: `/verify` (run), `/verify status` (show the last record and
  whether the diff has changed since), `/verify last` (print the record).
- **2.2 What a run does, in order, all via `pi.exec`:** (a) snapshot the
  diff hash with `snapshotDiff`; (b) resolve the canonical command with
  `resolveVerificationCommand`, falling back to the AGENTS.md ladder
  (`make verify`, then per-language defaults); (c) run formatter check,
  canonical broad verification, and lint/analyze if the repo defines one,
  recording exit code, duration, and a redacted tail of failing output
  (`redactFailureOutput` from `quality-gate.ts`, moved into `lib/` so
  both can import it); (d) if `AI_REVIEW_BASE_URL`/`AI_REVIEW_MODEL` are
  set, request one `cross-model-review.ts` round and record its label
  (`independent-review` vs `blind-self-review`) and outcome; (e) re-hash
  the diff and mark the record `stale` if it moved during the run. Each
  step that cannot run is recorded as `skipped` with the reason, never
  omitted (mirrors `prompts/before-done.md`'s rule).
- **2.3 Record format and location.** One JSON record per run at
  `~/.pi/agent/verify/<repo-slug>/<iso-timestamp>-<diffhash>.json`, plus
  the same summary as a `pi-harness-trace` entry (`event: "verification"`)
  so existing trace consumers see it. Outside the project tree on purpose:
  a verify record committed into a client repo is noise, and the session
  file already carries the trace. The human-facing output is the existing
  `ran:/skipped:/verdict:` table printed into the session, with the
  record path on the last line.
- **2.4 No gate (decision 5).** `/verify` registers no `turn_end`,
  `agent_end`, or `agent_settled` listeners and sends no follow-up
  messages. A `NOT DONE` verdict changes nothing about what the session
  does next. Test: assert the extension's registered event set is exactly
  the command registration plus `session_start` (for the record directory).
- **2.5 Reconcile the manual prompts.** `prompts/before-done.md` steps 2-4
  become "run `/verify`; paste its table"; step 1 (`git status`) and step 5
  (PR/CI state) stay manual because they are judgment, not mechanics.
  `skills/before-done/SKILL.md` step 6 and `skills/self-review/SKILL.md`
  step 2 either get a real `skills/before-done/scripts/local-review.sh`
  (a `curl` to `AI_STACK_HOST:8080`, inert when unreachable, same shape as
  `searxng-search.ts`) or lose the reference. Decide at implementation
  time based on whether the private script is worth publishing; either
  outcome removes the dangling path. `docs-verify`-style check: zero
  references to a script that does not exist.
- **2.6 Tests.** Unit: a fixture repo with a `Makefile` `verify` target
  that passes, one that fails, one whose command pipes through `head`
  without `pipefail` (must record `inconclusive`, not `pass`), and one
  where the diff changes mid-run (must record `stale`). Live: `/verify`
  inside a `pi` session on this repo itself; the record must show `npm
  test` as the canonical command and `DONE`.

### Piece 3 -- Cross-project resource discovery

- **3.1 Registry file, not settings sprawl (`~/.pi/agent/harness-resources.json`).**
  A short JSON document: a list of roots, each with an explicit `skills`
  allowlist and optional `prompts` allowlist, e.g. `{"root":
  "~/code/hermes-config", "skills": ["karpathy-guidelines"]}`. Absent file
  means no-op (same contract as `PI_PROJECT_SKILLS_REMOTE`). Kept outside
  this repo because it names machine-local paths, exactly the class of
  content README's extraction note says was removed from this release.
- **3.2 Overlay extension (`extensions/shared-resource-overlay.ts`).** On
  `resources_discover`, read the registry, resolve each allowlisted
  `skills/<name>` and `prompts/<name>.md` under each root (via `realpath`,
  so symlinked roots work the way `install.sh` links do), skip entries
  that do not exist with one warning each, and return `skillPaths` /
  `promptPaths`. Extensions are deliberately not shared this way: pi's
  hook cannot contribute them, and an extension from another repo would
  need this repo's `lib/` on its import path anyway.
- **3.3 Collision policy, made visible.** pi keeps the first skill found on
  a name collision and only warns. The overlay checks each contributed
  skill name against this repo's own `skills/` and the global
  `~/.pi/agent/skills/` and, on a collision, records a `routing` trace
  naming which copy won and why (registry entries are contributed after
  pi's built-in locations, so the local copy wins unless the registry
  entry sets `"prefer": true`). The point is that a diverged duplicate is
  reported, not silently shadowed.
- **3.4 Canonical copies.** Declare in this repo's README which shared
  skills are canonical here (`karpathy-guidelines`, `wiring-verify`,
  `docs-verify`, `local-summarize`, `before-done`) and register
  `~/.claude/skills/` symlinks for those against this repo, replacing the
  current mixed `agent-configs/pi` / `agent-configs/claude` links, so
  Claude Code and pi read the same file. The Hermes copy is a follow-up
  in `hermes-config` (decision 9): once pi reads the canonical copy, the
  Hermes directory can become a symlink or a documented re-export, but
  that change belongs to that repo's own review.
- **3.5 Cost check, since that is the stated reason overlays exist.** Live:
  `pi -p "list your available skills"` with and without the registry,
  comparing the system-prompt token count from `--mode json` output. The
  allowlist is the control; if a registry of three skills costs more than
  the three skills' name+description lines, something is being loaded
  that should not be.
- **3.6 Tests.** Unit: temp registry with one existing and one missing
  entry (one `skillPaths` entry, one warning); a collision fixture
  (trace names the winner); no registry file (hook returns `undefined`).
  Extend `tests/install-scope.test.ts` to assert the new overlay is
  linked and the registry file is *not* created by `install.sh`.

### Sequencing and exit criteria

- Piece 1 first; it is doc-and-test work plus one small extension and can
  land in a single PR. Exit: tag exists, README pins it, `npm test`
  includes 1.2-1.4, `UPGRADING.md` present.
- Piece 2 second, in two PRs: the extension with tests (2.1-2.4, 2.6),
  then the prompt/skill reconciliation (2.5). Exit: a `/verify` run on
  this repo produces a record and the `before-done` chain has no dangling
  script path.
- Piece 3 last, one PR plus a machine-local registry file written by hand.
  Exit: `wiring-verify` loads in a pi session started in a repo that does
  not contain it, from the copy in this repo, with the trace showing where
  it came from.

Every PR goes through the repo's own `/review` + `/before-done` (and, once
piece 2 lands, `/verify`) before it is opened -- the plan should be the
first consumer of its own evidence loop.

## Open questions

- Version source for 1.4: whether the peer `@earendil-works/pi-coding-agent`
  exposes its version at runtime cleanly, or whether reading its
  `package.json` via `import.meta.resolve` is the only path. Settle by
  reading the 0.84.2 package before writing the check.
- Whether `/verify` should accept an explicit command override
  (`/verify make integration`) in the first cut. Leaning no: an override
  is exactly how a narrower check gets recorded as the broad one.
- Whether `verify` records need a retention rule. One JSON file per run in
  a per-repo directory is small; decide only if the directory becomes
  noticeable.

## Watch items (not scope)

- **MCP bridging** -- promote to a plan on the second hand-wired MCP config
  (decision 3).
- **Hermes-side dedupe** -- make `hermes-config/skills/{karpathy-guidelines,
  wiring-verify}` read the canonical copy; belongs to that repo.
- **Private/public drift** -- 7 extensions and 6 skills differ between
  `agent-configs/pi` and this repo today. Not part of this plan, but piece
  1's tag gives the private repo a fixed ref to reconcile against.
